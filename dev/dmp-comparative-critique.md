# DMP v2 revision 7: independent comparative assessment

**Status:** informative assessment, not a normative DMP amendment. **Date:** 2026-09-24. This evaluates the [DMP implementation draft](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md) and [SEC-1 profile](../docs/DMP_v2_Security_Profile.md), not a released implementation. Its comparative judgments are architectural inferences, not measured performance or security certification.

## Decision frame

DMP's proposed niche is an opaque device message that retains its logical identity while moving between direct UART, BLE and raw radio, sometimes through relays, with optional pairwise end-to-end encryption. That is a narrower goal than a general resource API, typed vehicle bus, or distributed data fabric. The fair adoption question is whether that combination is required by actual deployments and whether owning its wire format, bootstrap and security lifecycle is worth the implementation and interoperability cost. A two-byte [minimal DMP core](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#23-overhead-accounting) is a useful option, but it omits identity, reliable delivery, routing, integrity and security. It cannot be compared to a complete protected exchange as if they provided the same service.

## What DMP gets right

1. **It states the layer boundary.** [§2](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#2-layering-and-network-ownership) assigns routing to an existing mesh when one exists and reserves its own forwarding for neighbor-only links. This avoids forcing a second mesh onto Thread, Bluetooth Mesh or another native network. CSP is a serious alternative for the raw-link router case, so this is a scope choice rather than an unprecedented capability. [libcsp router](https://libcsp.github.io/libcsp/protocolstack.html)
2. **Its receipt has a precise meaning.** [§7–8.1](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#7-replies-ack-and-errors) separate final-endpoint acceptance from application result, unknown timeout outcome and durable exactly-once behavior. This directly addresses command ambiguity when a relay or ACK is lost. CoAP also distinguishes message acknowledgement from request response; DMP's value is the explicit device-command policy, not invention of that distinction. [CoAP](https://www.rfc-editor.org/rfc/rfc7252.html)
3. **The security trust boundary is unusually explicit for this draft.** [SEC-1 §§S4–S9](../docs/DMP_v2_Security_Profile.md#s4-traffic-keys-identity-and-confirmation) defines association-bound identity, immutable authenticated routing fields, replay state, reboot/rekey handling and gateway termination. It correctly distinguishes authentication, confidentiality, freshness and authorization. OSCORE is mature prior art for similar intermediary-visible/protected-field separation; DMP still needs independent cryptographic implementation review. [OSCORE](https://www.rfc-editor.org/rfc/rfc8613.html)
4. **Bounded-resource failure is treated as protocol behavior.** [§18](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#18-sleeping-nodes-queues-and-expiry) and [SEC-1 §S3.2](../docs/DMP_v2_Security_Profile.md#s32-pre-authentication-resource-admission) require quotas and control progress before claiming reliable admission. This matters on narrowband radios and constrained RAM; libcsp's pools and explicit packet ownership show this can be implemented rather than left as prose. [libcsp packet API](https://libcsp.github.io/libcsp/api/csp_types_h.html)

## Main reservations

1. **The strongest rationale is still an unproven combination.** CSP already covers small routed datagrams across serial/radio-like interfaces, while CoAP+OSCORE+EDHOC supplies standardized protected exchanges. DMP's differentiator is one opaque logical identity and E2E trust contract across direct and transparent raw-radio paths. The draft has no measured RAM, airtime, energy, interoperability or independent security evidence proving this combined stack beats a CSP or CoAP-based application in the actual DTrack deployment. [DMP §23.1](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#231-evaluation-before-wire-format-optimization)
2. **Security establishment and operations may dominate a small payload.** A direct protected telemetry frame is specified as 23 bytes of DMP overhead with small counters; a comparable immediate protected request/result/result-ACK exchange is 75 bytes of DMP overhead, and loss-free PSK/XX bootstrap is calculated at 274/406 bytes, before binding bytes or retries. These are draft arithmetic, not measurements. [§23](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#23-overhead-accounting) For intermittent BLE or radio peers, re-establishment after volatile-state loss and provisioning/verification workflow deserve priority over promoting the two-byte minimum.
3. **Whole-message fragment retry is a material radio cost.** [§8 and §11](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#11-fragmentation-and-reassembly) make reassembly bounded and unambiguous, but retransmit every fragment after one loss. CoAP Q-Block can request missing blocks, though it adds its own layer and is optional. [RFC 9177](https://www.rfc-editor.org/rfc/rfc9177.html) DMP wisely defers selective recovery; adoption should keep large objects out of the base message path until real loss/airtime tests justify an extension.
4. **A draft with many optional modules invites profile fragmentation.** [§1, §12.3 and §19](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#1-scope-and-conformance) require manifest agreement but have no generic capability negotiation. A Core-only node, a reliable node and an SEC-1 node can all claim DMP while being unable to exchange a service. This is manageable inside one product with fixed profiles, but weak for an open ecosystem. CoAP RFCs and MAVLink dialect tooling offer a firmer shared starting point. [CoAP](https://www.rfc-editor.org/rfc/rfc7252.html), [MAVLink dialects](https://mavlink.io/en/guide/define_xml_element.html)
5. **Opaque payloads defer interoperability to application profiles.** [§12](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#12-payload-descriptor-and-application-profiles) avoids paying serializer overhead on every frame, but schema governance, code generation, versioning and tooling still have to be built or adopted. Cyphal's DSDL and MAVLink XML address this part directly. [Cyphal specification](https://specification.opencyphal.org/Cyphal_Specification.pdf), [MAVLink serialization](https://mavlink.io/en/guide/serialization.html)

## Adoption judgment and focused next steps

Choose DMP for a product-controlled set of endpoints **only if** the same opaque command/telemetry contract must cross direct UART/BLE and transparent raw-radio relays, the trust boundary really must exclude those relays, and the team accepts ownership of a new protocol implementation. Prefer CSP first for an embedded routed datagram network where its existing router/RDP/fragment tools and deployment security suffice; prefer CoAP+OSCORE+EDHOC for resource-style requests on a suitable binding where standards interoperability outweighs DMP's tailored message semantics. MAVLink, Cyphal and Zenoh are strongest when their respective telemetry dialect, typed bus or pub/sub/query model is already the application model. These are fit judgments, not claims that any candidate universally wins.

1. **Freeze two concrete deployment manifests:** one direct UART/BLE pair and one raw-radio multihop path, with actual MTU, loss/sleep bounds, credentials, quotas and command semantics. This converts optional-feature prose into implementable conformance targets. [DMP §12.3](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#123-required-deployment-manifest)
2. **Build one equivalent-workload comparison:** protected command/result and short telemetry under identical acceptance semantics, including cold/warm sessions, retransmissions, peak RAM and airtime. Compare against the nearest implementable CSP and CoAP stacks, not only their base headers. Publish configurations and raw observations. [DMP §23.1](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#231-evaluation-before-wire-format-optimization)
3. **Require independent parser and SEC-1 interoperability/fault review before release:** two implementations must agree on vectors, malformed frames, loss/restart/rotation, authorization and overload behavior. A normative draft and test vectors are not deployment evidence. [DMP §24](../docs/DMP_v2_Device_Messaging_Protocol_Specification.md#24-implementation-and-release-sequence)

**Uncertainties:** No candidate was benchmarked on the same hardware/path in this assessment. Documented transport support does not prove the required BLE GATT or raw-LoRa binding is ready. Library versions and deployments can differ from the linked current documentation; in particular, the Cyphal stable v1.0 PDF marks UDP experimental, while active libraries can support later protocol revisions. No claim here establishes formal verification or a completed DMP implementation.
